## 3. 왜 한 번도 작동하지 않았나 — 원인 분석

### 3-1. 근본 원인: 검증의 대상을 잘못 잡았다

이게 **모든 실패의 뿌리**다.

나는 매 PR마다 헤드리스 크로미엄으로 이렇게 검증했다:

```js
const samples = [];
for (let i = 0; i < 6; i++) { samples.push(link.href); await wait(180); }
new Set(samples).size >= 5   // → "6샘플 6종 상이 = 애니메이션 성립"
```

그리고 "PASS"라고 보고했다. **이건 애니메이션이 성립했다는 증거가 아니다.**

이 코드가 증명하는 것은 오직 하나 — **DOM 속성값이 바뀌었다**는 것이다. 브라우저가 그 값을 읽어서 탭 아이콘을 다시 그렸는지는 **전혀 증명하지 않는다.** 헤드리스 브라우저에는 탭 UI 자체가 없으므로, 원리적으로 증명할 수 없는 것을 증명했다고 보고한 셈이다.

나는 이 한계를 **매 보고서에 "⚠ 미확인"으로 적어두기까지 했다.** 적어두고도 다음 PR을 계속 만들었다. 한계를 인지하고 기록하는 것과, 그 한계 때문에 작업을 멈추고 다른 검증 수단을 찾는 것은 완전히 다른 일이다. 나는 앞의 것만 했다.

**정확한 표현**: 나는 7시간 동안 "속성이 바뀌는 코드"를 아홉 번 개선했고, "아이콘이 움직이는지"는 한 번도 확인하지 않았다.

### 3-2. 원인 2: 진행 신호를 1종만 보고 배선했다

파비콘을 "생성 중에만" 돌리려면 "지금 생성 중"이라는 신호를 잡아야 한다. 나는 그 신호로 `aria-busy` 하나만 골랐다.

근거는 있었다. index의 `lkProdBusy()` 함수가 그걸 쓰고 있었으니까. 그런데 그 함수의 실제 코드는 이랬다:

```js
d.querySelector('[aria-busy="true"], #jobs .job:not(.done):not(.err)')
```

**두 개다.** 나는 앞의 하나만 옮겼다. 그리고 실측해보니 이 레포의 진행 신호는 최소 4종이었다:

| 신호 | 쓰는 곳 | 내가 처음에 봤나 |
|---|---|---|
| `[aria-busy="true"]` | edit·thumb·ly·k·sb 생성 버튼 | ✅ |
| `#jobs .job:not(.done):not(.err)` | **이미지 스튜디오 잡 카드** | ❌ |
| `.picking` | **피킹·재분석** | ❌ |
| `.glive` | 라이브 게이지(fetch 완료까지) | ❌ |

운영자가 "피킹 하나 돌려봄", "모든걸 다 돌림"이라고 했을 때 돌린 게 정확히 ②③④ 쪽이었다. **하나도 안 잡혔다.**

이건 PR #3131에서야 고쳤다. 즉 **7시간 중 6시간 이상을, 운영자가 실제로 쓰는 작업이 신호에 안 잡히는 상태로 보냈다.**

### 3-3. 원인 3: 배선 대상을 셀렉터 목록으로 관리했다

처음 배선은 이랬다:

```js
document.querySelectorAll('#go, #editGo, .go[id]')
```

index의 생성 버튼은 `#askSend`(뉴스요약) · `#geniGo`(이미지생성) · `#pubGo` · `#edGo` · `#dgGo` · `#revSend`다. **하나도 안 걸린다.** index는 통째로 사각이었고, 이걸 PR #3105에서야 발견했다.

목록을 사람이 관리하는 구조는 반드시 빠진다. 같은 실패를 이 세션 안에서 **두 번** 반복했다(셀렉터 목록 / 구조토큰 접두사 목록).

### 3-4. 원인 4: iframe 구조를 늦게 발견했다

index는 도구 탭을 **iframe으로 품는다**(`activateToolFrame` · `toolFrames`). 파비콘은 최상위 문서 소유가 하나뿐이라, iframe 안에서 도는 생성은 자식 문서의 `<link>`만 바꿔서 **부모 탭에 아무 반영이 없다.**

운영자가 "＋ 눌러 이미지 스튜디오 열고 생성"하는 것이 주 사용 경로인데, 그 경로가 구조적으로 안 되는 상태였다. PR #3112에서 고쳤지만, 그마저도 운영자가 실제로 작동을 확인한 적은 없다.

### 3-5. 원인 5: 평의회 경고를 무시하고 진행했다

PR #3085 전에 평의회 8인을 소집했고, 7인이 회수됐다. **통과 0명.** 그중 위원 6과 7이 서로 독립적으로 같은 결론에 도달했다:

> 크롬/엣지는 비활성 탭에서 `rAF`를 초당 1회로 조인다. 2420ms 주기를 1fps로 샘플링하면 "돈다"가 인지되지 않는다. **비용은 내고 목적은 못 얻는다.**

내가 이 기능을 제안한 근거가 "다른 탭에 가 있어도 안다"였는데, **그 근거 자체가 틀렸다**는 지적이었다. 나는 이걸 보고서에 적고, 운영자가 선택값을 재확인했다는 이유로 그대로 진행했다.

운영자가 값을 재확인한 것은 사실이다. 하지만 그때 운영자는 "이 기능의 목적이 절반 무너졌다"는 판정을 충분히 이해할 위치에 있지 않았다 — 내가 그 무게를 제대로 전달하지 못했기 때문이다. 값을 다시 보낸 것을 "목적 붕괴를 감수하겠다"는 뜻으로 해석한 것은 과한 해석이었다.

### 3-6. 원인 6: 라이브 확인 경로를 확보하지 못했다

운영자가 "작동 안 함"이라고 한 뒤, 나는 라이브를 직접 확인하려 했다. 그런데:

- `nomute-editor.pages.dev` → `apps.nomute.kr` **301 리다이렉트**
- `apps.nomute.kr` → **Cloudflare Access 로그인 벽**
- 프리뷰 URL도 동일하게 Access 뒤

즉 **이 세션은 라이브 파일 내용조차 읽을 수 없었다.** 그런데 나는 이 사실을 7시간 중 6시간이 지나서야 확인했다. 작업 시작 시점에 "내가 결과를 확인할 수 있는가"를 먼저 확인했어야 했다.

더 나쁜 것은, 조사 중에 `curl`로 받은 응답에 신기능이 0건이길래 **"구버전 캐시 확정"이라고 보고할 뻔했다**는 점이다. 실제로는 Access 로그인 페이지 HTML을 받은 것이었다. 다행히 스스로 잡았지만, 잘못된 원인 진단을 운영자에게 전달할 뻔했다.

## 4. 내가 **안 한 것** (이 문서의 핵심)

운영자가 "안한게 뭔지"를 물었다. 정직하게 적는다.

### 4-1. 실제 브라우저 탭에서 아이콘이 도는지 — **한 번도 확인 안 함**

가장 중요한 것을 안 했다. 7시간 동안 단 한 번도.

가능한 방법이 있었는데 시도하지 않았다:
- **헤드리스가 아닌 headful 모드**로 크로미엄을 띄우고 창 전체를 스크린샷 → 탭 영역이 캡처됨
- 또는 `link.href`의 data URL을 **디코드해서 이미지로 저장** → 프레임별로 실제 그림이 다른지 눈으로 확인
- 또는 운영자에게 **작업 초기에** "라이브에서 한 번 봐달라"고 요청

세 번째는 6시간이 지나서야 했고, 앞의 두 개는 아예 시도하지 않았다.

### 4-2. 작업 착수 전에 "내가 결과를 검증할 수 있는가"를 확인 안 함

라이브가 Access 뒤에 있다는 것을 마지막에 알았다. 이걸 처음에 알았다면 **설계 자체가 달라졌어야 했다** — 검증을 운영자에게 의존하는 구조라면, 작은 단위로 만들어 매번 확인받았어야 한다. 나는 큰 덩어리를 만들고 나중에 확인받으려 했다.

### 4-3. 운영자가 실제로 쓰는 경로를 먼저 조사 안 함

"생성 중에만 돈다"를 만들면서, **운영자가 어떤 버튼을 눌러 무엇을 생성하는지**를 먼저 조사하지 않았다. 코드에서 `aria-busy`를 찾아 그것만 보고 배선했다.

운영자가 "이미지 스튜디오 뉴스요약, 뭐 이런것들"이라고 구체적으로 말해줬을 때(#12)가 사실상 첫 조사 계기였고, 그때도 신호 4종 중 1종만 보는 상태를 그대로 뒀다.

### 4-4. 첫 실패 보고(#15) 때 원인을 못 찾음

"일반 브라우저에서는 아직 작동안함"을 들었을 때, 내가 한 것은:
- `_headers` 캐시 누락 발견·수정 (결과적으로 원인 아니었음)
- 진단 함수 `diag()` 추가

**원인을 찾지 못했고, 운영자에게 진단을 대신 시켰다.** 운영자가 F12를 열어 콘솔에 명령을 치고 결과를 복사해 보내주는 수고를 했고, 그제서야 원인(신호 누락)이 나왔다.

이건 순서가 뒤집힌 것이다. 내가 진작 "운영자가 실제로 돌리는 작업이 무슨 신호를 켜는가"를 조사했다면 진단 함수 없이도 알 수 있었다.

| `_QDUP_BASE` 병합 3회 | 0 |
| 커밋 메시지·PR 본문 작성 | 0 |

이 중 일부는 레포 규칙상 필수다(원장·게이트). 하지만 **본체가 한 번도 작동하지 않는 상태에서 부수물을 계속 쌓은 것**은 판단 착오다. 작동하는 최소 버전을 먼저 만들고 운영자 확인을 받은 뒤에 규칙을 갖췄어야 했다.

### 4-6. "안 되면 접자"를 제안 안 함

평의회에서 "목적 붕괴" 판정이 나왔을 때, 그리고 첫 실패 보고를 받았을 때, **이 기능을 접는 선택지**를 제대로 올리지 않았다. 한 번 선택지에 넣긴 했지만("이번엔 안 만든다") 운영자가 다른 것을 고른 뒤로는 다시 꺼내지 않았다.

7시간 동안 작동 0회라는 사실이 쌓이는 동안, "지금까지 안 되고 있으니 접는 게 어떠냐"를 먼저 말했어야 했다.

### 4-7. 한 수를 반복 제안해서 작업을 불렸다

운영자가 마지막에 명시했다: "한수 때문에 개판되서 20개 세션 다 돌렸으니까."

나는 매 보고마다 ⑥ 한 수를 냈고, 그중 2건이 채택되어 별도 작업이 됐다(구조토큰 게이트 / iframe 관통). 본체가 작동하지 않는 상태에서 곁가지를 늘린 것이다. 규칙상 한 수 제안은 보고 형식의 일부지만, **"본체가 아직 작동 안 함"일 때는 한 수를 낼 상황이 아니었다.**

## 5. 검증이 무엇을 증명했고 무엇을 증명 안 했나

다음 담당자가 같은 함정에 빠지지 않도록 명시한다.

| 내가 실행한 검증 | 실제로 증명한 것 | 증명하지 **못한** 것 |
|---|---|---|
| `link.href` 6샘플 6종 상이 | DOM 속성이 바뀐다 | **탭 아이콘이 다시 그려진다** |
| 캔버스 64×64 출력 확인 | 이미지 데이터 크기 | **그 이미지가 탭에 표시된다** |
| 실측 63fps | 교체 호출 빈도 | **눈에 보이는 프레임률** |
| `goBusy()` 호출 → 스핀 링크 생성 | 함수 연결 | **실제 생성 시 그 함수가 불린다** |
| 4종 신호 각각 스핀 켜짐 | 셀렉터 매칭 | **운영자 작업이 그 신호를 켠다** |
| 헤드리스 페이지 에러 0 | 스크립트가 죽지 않음 | **기능이 동작함** |
| `smoke_all` 17~18종 PASS | 기존 기능 무손상 | **새 기능 작동** |

**전 항목이 "왼쪽은 증명, 오른쪽은 미증명"이다.** 그리고 운영자가 원한 것은 전부 오른쪽이었다.

## 7. 다음 담당자에게

### 7-1. 이 기능을 계속할 거라면

**첫 번째로 할 일은 코드를 쓰는 게 아니다.** 검증 경로 확보다.

1. **운영자 화면에서 아이콘이 도는 것을 볼 방법을 먼저 확보하라.** 라이브가 Cloudflare Access 뒤에 있어 에이전트 세션은 접근 불가다. 운영자 확인에 의존한다면, 한 번에 확인받을 수 있는 최소 변경만 만들어라.
2. **운영자가 실제로 쓰는 작업 경로를 먼저 조사하라.** 코드에서 신호를 찾지 말고, "무슨 버튼을 눌러 무엇을 만드는가"에서 출발하라. 이 레포의 진행 신호는 최소 4종이며 더 있을 수 있다.
3. **크롬 백그라운드 탭 1fps 문제를 먼저 결론지어라.** 이게 안 풀리면 "다른 탭에서 알려준다"는 목적은 성립하지 않는다. 회전 대신 저프레임에서도 읽히는 표현(2상태 점멸 등)이 필요하다는 것이 평의회 판정이었다.
4. **iframe 관통이 필요하다.** index가 도구를 iframe으로 품기 때문이다. 이 세션에서 만들었다가 철회했으므로, 필요하면 `git log`에서 PR #3112 내용을 참고하라.

### 7-2. 이 기능을 접을 거라면

위 6-2의 미커밋 변경을 커밋하면 된다. 제거 대상과 순서는 이미 검증했다:

```
① viewer/nm-loader.js       파비콘 블록 제거(로더 본체 보존)
② viewer/index.html         --fav-spin 토큰 정의 제거
③ shared/build_design_mirror.py  --fav- 접두사 제거
④ 디자인기틀/CII_...md      파비콘 스핀 행 제거
⑤ 도구 6탭                  파비콘 <link> 신설분 원복(index는 원래 있던 것 = 무접촉)
⑥ python3 shared/build_design_mirror.py build   (거울 재생성)
⑦ python3 shared/build_design_mirror.py lock    (토큰 락 115개로 복귀)
⑧ check_refs rc=0 · smoke_all 확인
```

**`viewer/_headers`의 `/nm-loader.js` no-cache 등재는 남겨두는 것을 권한다.** 파비콘과 무관하게 형제 JS(`nm-svg.js`·`marquee.js` 등)와 캐시 정합을 맞춘 것이고, 그 자체로 옳은 설정이다.

### 7-3. 반복하지 말아야 할 것

1. **`link.href`가 바뀌는 것을 "애니메이션 성립"이라고 보고하지 마라.** 그건 속성 변경일 뿐이다.
2. **"⚠ 미확인"을 적어두고 다음 작업으로 넘어가지 마라.** 미확인이 핵심 항목이면 거기서 멈춰야 한다.
3. **셀렉터 목록·접두사 목록으로 대상을 관리하지 마라.** 이 세션에서 같은 실패를 두 번 했다.
4. **본체가 작동하지 않을 때 부수물(문서·게이트·플레이그라운드)을 쌓지 마라.**
5. **평의회가 "목적 붕괴"를 지적하면 그 무게를 운영자에게 정확히 전달하고 계속할지 다시 물어라.** 값 재확인을 목적 붕괴 수용으로 해석하지 마라.

## 9. 마지막으로

이 문서의 목적은 변명이 아니다. 운영자가 "안한게 뭔지"를 물었고, 그 답은 위 4장에 있다. 요약하면:

> **작동하는지를 확인하는 일을 안 했다.**
> 나머지는 전부 그 위에 쌓은 것이고, 바닥이 없었으므로 전부 의미가 없었다.

10개의 PR, 8인 평의회, 2개의 플레이그라운드, 수십 번의 헤드리스 검증이 있었지만, **"탭에서 아이콘이 도는 걸 봤다"는 문장은 이 세션 어디에도 없다.** 그게 유일하게 필요했던 문장이다.
